# 01 数制与固定位模式

## 1. 学习目标

完成本章后，你应能：

- 用位权展开解释任意进制整数；
- 在二进制、十六进制与十进制之间转换；
- 解释“固定位宽”如何限制可表示的数值范围；
- 说明 BitVector 为什么只保存位模式，而不隐含符号；
- 用 CLI/API 验证位模式与数值解释的差异。

## 2. 理论：位置记数法

一个 `n` 位无符号二进制字 `b[n-1] ... b[1] b[0]` 的数值是：

\[
V = \sum_{i=0}^{n-1} b_i 2^i
\]

其中 `b[i]` 只能是 0 或 1，`i=0` 是 LSB，`i=n-1` 是 MSB。

n 位无符号数的范围：

\[
0 \le V \le 2^n - 1
\]

| 位宽 n | 无符号范围 |
| --- | --- |
| 4 | 0 … 15 |
| 8 | 0 … 255 |
| 16 | 0 … 65535 |
| 32 | 0 … 4294967295 |
| 64 | 0 … 18446744073709551615 |

### 2.1 二进制与十六进制

十六进制的每一位权重是 16 的幂，一位十六进制数字恰好对应 4 个二进制位。
因此从低位向高位每 4 位分组即可得到十六进制：

```text
101101.011₂
= 0010 1101 . 0110₂
= 2D.6₁₆
```

RadixLab 的 `radixlab-cli --input ... --from ... --to ...` 和
`POST /api/v1/convert` 处理带小数点的精确转换，详见根目录 README。

### 2.2 位模式不是数值

BitVector 保存的是：

```text
pattern = 150
width   = 8
```

它对应的位串是 `10010110`，但这个模式可以：

- 作为无符号数解释为 150；
- 作为 8 位补码解释为 −106；
- 作为 8 位 BCD 解释为十进制 96（`1001` = 9，`0110` = 6），而不是 150；
- 作为 Gray Code 解读为另一个无符号数；
- 作为带校验字的一部分。

因此 BitVector 的接口明确把 `pattern()`、`toUnsigned()`、`toBinary()` 与
`toHex()` 和符号解释分开。符号解释必须由 `signed_encoding` 提供。

## 3. 算法：解析与输出

### 3.1 按权累加（Horner 形式）

从最高位向右扫描：

```text
value = 0
for each bit b:
    value = value * 2 + b
```

十六进制同理，把基数换成 16。

### 3.2 固定宽度截断不是编码

如果只保留低 4 位，`10010110` 会变成 `0110`。这不是“4 位编码成功”，而是
丢弃了高位。RadixLab 的编码函数会先检查范围并抛出 `RangeError`，不会用
截断掩盖不可表示。

## 4. C++ 实现位置

- 头文件：`cpp-core/include/radixlab/encoding/bit_vector.hpp`
- 源文件：`cpp-core/src/encoding/bit_vector.cpp`
- 测试：`cpp-core/tests/test_bit_vector.cpp`

BitVector 的关键行为：

| 方法 | 语义 |
| --- | --- |
| `BitVector(pattern, width)` | 检查宽度 1–64 和 pattern 是否落在位宽内 |
| `fromBinary("1010")` | 解析固定位串，长度即宽度 |
| `fromHex("AF", 8)` | 解析十六进制，值必须适配宽度 |
| `bit(i)` | 读取索引 i，0 为 LSB；越界抛异常 |
| `toBinary()` | 按 MSB→LSB 补齐到固定宽度 |
| `toHex()` | 按 nibble 补齐输出大写十六进制 |
| `shiftLeft/Right` | 逻辑移位；空位补 0，移出位丢弃 |
| `bitwiseAnd/Or/Xor/Not` | 要求位宽一致；NOT 只作用于声明位宽 |
| `withBit/flipBit` | 显式设置或翻转某一位 |

`cpp_int` 用于掩码和移位，避免 64 位有符号溢出和移位越过本机字长的未定义行为。

## 5. API 与 CLI 实验

### 5.1 十进制 → 十六进制（原有 RadixLab）

```bash
./cpp-core/build/radixlab-cli --input 150 --from 10 --to 16
# 96
```

注意：这里的 `96` 是十六进制字符串，不是十进制九十六。

### 5.2 二进制模式解析（通过编码 CLI 的 Gray/有符号功能观察）

```bash
./cpp-core/build/radixlab-cli encoding \
  --operation signed-decode --bits 10010110 \
  --encoding TWOS_COMPLEMENT --json
```

8 位补码 `10010110` 解出的值是 −106；同一个模式作为无符号解释则是 150。
这两个结果都不矛盾，因为使用的是不同解释规则。

### 5.3 API 对照

```bash
curl -sS http://localhost:8080/api/v1/convert \
  -H 'Content-Type: application/json' \
  -d '{"number":"10010110","fromBase":2,"toBase":10}'
```

返回 `{"result":"150",...}`，这是无符号数值解释。符号解释需要调用
`/api/v1/encoding/signed/decode`。

## 6. 可复现实验：59 的三种看法

1. 计算 59 的二进制：

   ```text
   59 = 32 + 16 + 8 + 2 + 1 = 111011₂
   ```

2. 补零到 8 位：`00111011`。

3. 验证十六进制：`0011 1011 = 3B`。

4. 运行：

   ```bash
   ./cpp-core/build/radixlab-cli --input 59 --from 10 --to 16
   # 3B
   ./cpp-core/build/radixlab-cli --input 59 --from 10 --to 2
   # 111011
   ```

5. 观察补零不会改变数值，但会改变固定宽度位模式：

   ```text
   111011₂ = 00111011₂ = 59₁₀
   ```

6. 打开 Encoding Lab 的 BCD 标签，输入 59，比较：

   ```text
   普通二进制: 111011
   BCD:        0101 1001
   ```

   后者不是 59 的 8 位二进制，而是两个十进制数字的分别编码。

## 7. 常见误区

- **把十六进制 `10` 当成十进制 10**：十六进制的 `10` 等于十进制 16。
- **认为前导零改变数值**：`0011` 与 `11` 数值相同，但固定宽度的位模式不同。
- **把位索引当位权**：索引 7 的位权是 128，不是 7。
- **用截断实现溢出检查**：截断只保留了低位，原来不可表示的值仍不可表示。
- **在 BCD 上下文用普通二进制解释**：`01011001` 在 BCD 中表示 59，在二进制中是 89。
- **把字符串写成小端顺序**：本项目输出始终按 MSB→LSB 显示，LSB 在右侧。

## 8. 练习

1. 将 `101101₂` 和 `2D₁₆` 转为十进制，并验证二者相等。
2. 8 位无符号数最大是多少？加 1 后固定 8 位会发生什么？
3. `11111111` 在无符号 8 位、8 位补码、BCD 中分别如何解释？
4. 计算 `A5₁₆` 的 8 位二进制表示。
5. 为什么 BitVector 不直接提供“把模式当有符号数”的隐式转换？

### 答案与验证

1. `101101₂ = 45`；`2D₁₆ = 2×16+13 = 45`。可用
   `radixlab-cli --input 101101 --from 2 --to 10` 和
   `--input 2D --from 16 --to 10` 验证。
2. 最大值是 `255 = 11111111₂`。加 1 得到 `100000000₂`，超出 8 位范围；
   若只保留 8 位会变成 0，但这是截断，不是合法的 8 位无符号加法结果。
3. 无符号：255；8 位补码：−1；BCD：`1111` 是非法码字，因此不能解释为一个
   合法 BCD 数。这个例子说明解释规则决定合法性。
4. `A5₁₆ = 1010 0101₂`。
5. 隐式转换会隐藏“编码形式 + 位宽”的前提，容易让 `11111111` 在不同上下文中
   被错误地当成同一个数。显式 API 强制调用者选择解释规则。
